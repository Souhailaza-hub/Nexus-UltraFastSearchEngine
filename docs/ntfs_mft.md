# NTFS MFT enumeration research

The MFT path will use `FSCTL_ENUM_USN_DATA` against a volume handle opened as `\\.\X:`. Microsoft documents the control as an NTFS volume enumeration operation; each call returns a next-start file reference number followed by variable-length USN records. The request starts at file reference zero and subsequent requests use the returned continuation reference. The parser must advance by each record's `RecordLength`, validate the output bounds, and explicitly handle the advertised record major version. See the [FSCTL_ENUM_USN_DATA documentation](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_enum_usn_data), [MFT_ENUM_DATA_V0](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ns-winioctl-mft_enum_data_v0), and [USN_RECORD_V2](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ns-winioctl-usn_record_v2).

The record contains the file reference, parent reference, name, file attributes, timestamp, and USN, but it does not contain file size. A bounds-checked V2 parser and NTFS volume-root enumerator are implemented. The enumerator resolves parents only after collecting the complete MFT listing; if any parent cannot be resolved, it discards the MFT results and falls back to recursive scanning. It uses `GetFileAttributesExW` for each reconstructed path to retrieve size and the file's actual modification timestamp. That preserves metadata semantics but may limit the speedup and increases temporary memory use. The parser has synthetic-buffer tests; a full-volume MFT run has not yet been verified on a real NTFS volume. Volume-handle access failures fall back to the recursive scanner and are counted in `mft_fallbacks`.
